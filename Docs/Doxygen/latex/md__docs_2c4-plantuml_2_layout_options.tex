Plant\+UML uses \href{https://www.graphviz.org/}{\texttt{ Graphviz}} for its graph visualization. Thus the rendering itself is done automatically for you -\/ that it one of the biggest advantages of using Plant\+UML.

...and also sometimes one of the biggest disadvantages, if the rendering is not what the user intended.\hypertarget{md__docs_2c4-plantuml_2_layout_options_autotoc_md2}{}\doxysubsection{\texorpdfstring{Overall Guidance}{Overall Guidance}}\label{md__docs_2c4-plantuml_2_layout_options_autotoc_md2}

\begin{DoxyEnumerate}
\item Be minimal in the use of all directed relations -\/ introduce the fewest possible directed {\ttfamily Rel\+\_\+} and {\ttfamily Lay\+\_\+} statements that achieve the desired layout. One way to do this is to immediately remove any of these you experiment with when they don\textquotesingle{}t actually affect the layout at all. And of course you will remove the ones that affect it the layout in a negative way.
\item With dynamic rendering tools (e.\+g. VS Code plugin) do NOT trust the first rendering as it is shifty when adding code because you do not know exactly when it grabs the current unsaved code. Wait for a bit or close and reopen preview panel.
\end{DoxyEnumerate}\hypertarget{md__docs_2c4-plantuml_2_layout_options_autotoc_md3}{}\doxysubsection{\texorpdfstring{Layout Practices}{Layout Practices}}\label{md__docs_2c4-plantuml_2_layout_options_autotoc_md3}
These are intended to correlate to the layout engine’s algorithm, but have (as of this writing) been determined by trial and error -\/ not a code review.

Please read through all practices before starting.


\begin{DoxyEnumerate}
\item Create all components, containers and boundaries first -\/ in order top to bottom or left to right.
\item Use {\ttfamily Rel} (directionless) to create initial relationships.
\item If layout is not as desired, modify {\bfseries{some}} Rel statements to contain direction {\ttfamily Rel\+\_\+\{direction\}} to force shape layouts.
\item If the layout is not as desired, sparingly add {\ttfamily Lay\+\_\+\{direction\}} to force any layouts that {\ttfamily Rel\+\_\+\{direction\}} does not correct.
\item For both {\ttfamily Lay\+\_\+\{direction\}} and {\ttfamily Rel\+\_\+\{direction\}} statements used above\+:
\begin{DoxyEnumerate}
\item Exhaust attempts to get a working layout with {\ttfamily Rel\+\_\+\{direction\}} before adding {\ttfamily Lay\+\_\+\{direction\}}
\item Try to introduce the fewest possible directed statements (of either type) that result in the desired layout.
\item Immediately back out any directed statements that do not change the layout at all.
\item Order inner objects first when it creates the desired result (enclosing objects tend to follow suit when child objects are ordered).
\item When ordering multiple objects, only specify one relationship and, if possible in the same direction. For example if you want entity1 =\texorpdfstring{$>$}{>} entity2 =\texorpdfstring{$>$}{>} entity3, then {\ttfamily Rel\+\_\+\+R(entity1,entity2)} and {\ttfamily Rel\+\_\+\+R(entity2, entity3)} is the minimum possible statements and they all specify the same direction.
\item Try NOT to apply directed statements to both inner elements and enclosing elements to force relationships that aren\textquotesingle{}t working out.
\item Make all orderings at the same nesting level whenever possible.
\item Do NOT create duplicated, opposite direction statements in an attempt to force or ensure relationships as it does not affect the results. For instance if you have {\ttfamily Lay\+\_\+\+R(entity1,entity2)} which is not working as desired and then also add the opposing one as {\ttfamily Lay\+\_\+\+L(entity2,entity1)} -\/ it does not help with forcing layouts to be as you want them. It might help to use {\ttfamily Lay\+\_\+L} {\bfseries{instead of}} {\ttfamily Lay\+\_\+R}, but not both together.
\end{DoxyEnumerate}
\item Do not create an "{}\+All enclosing"{} boundary -\/ the code for processing relationships seems to struggle with relationships inside this. Additionally, {\ttfamily SHOW\+\_\+\+FLOATING\+\_\+\+LEGEND()} will not display inside the All enclosing boundary.
\item Legend statements must come after at least one usage of each of the elements you want the legend to contain.
\end{DoxyEnumerate}\hypertarget{md__docs_2c4-plantuml_2_layout_options_autotoc_md4}{}\doxysection{\texorpdfstring{LAYOUT\+\_\+\+TOP\+\_\+\+DOWN() or LAYOUT\+\_\+\+LEFT\+\_\+\+RIGHT() or LAYOUT\+\_\+\+LANDSCAPE()}{LAYOUT\+\_\+\+TOP\+\_\+\+DOWN() or LAYOUT\+\_\+\+LEFT\+\_\+\+RIGHT() or LAYOUT\+\_\+\+LANDSCAPE()}}\label{md__docs_2c4-plantuml_2_layout_options_autotoc_md4}

All of that is the reason, C4-\/\+Plant\+UML uses colors and prefer also to enable a layout without {\ttfamily \texorpdfstring{$<$}{<}\texorpdfstring{$<$}{<}stereotypes\texorpdfstring{$>$}{>}\texorpdfstring{$>$}{>}} and with a legend. This can be enabled with {\ttfamily LAYOUT\+\_\+\+WITH\+\_\+\+LEGEND()}.

Instead of a static legend (activated with {\ttfamily LAYOUT\+\_\+\+WITH\+\_\+\+LEGEND()}) a calculated legend can be activated with {\ttfamily SHOW\+\_\+\+LEGEND(?hide\+Stereotype, ?details)}.

The calculated legend has following differences\+:


\begin{DoxyItemize}
\item only relevant elements are listed
\item custom tags/styles are supported
\item stereotypes can remain visible (with {\ttfamily SHOW\+\_\+\+LEGEND(false)})
\item details can be displayed in different sizes via the {\ttfamily \$details} argument
\begin{DoxyItemize}
\item {\ttfamily \$details = Small()} .. default; details are displayed with a smaller size compared to the legend labels
\item {\ttfamily \$details = Normal()} .. details and labels are displayed with same size
\item {\ttfamily \$details = None()} .. only the labels are displayed
\item if {\ttfamily \$legend\+Text} contains {\ttfamily \textbackslash{}n} then the text before is the label and the text behind the details
\end{DoxyItemize}
\item {\bfseries{{\ttfamily SHOW\+\_\+\+LEGEND()} has to be last call in the diagram}}
\end{DoxyItemize}
